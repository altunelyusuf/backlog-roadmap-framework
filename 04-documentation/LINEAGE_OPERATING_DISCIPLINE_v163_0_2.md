# Lineage Operating Discipline — v163.0.2

**What this is.** How a lineage is started and run, in one page. SHACL enforces; this file only tells the agent the order of work and the principles behind it. It holds no ruling text.

**Where everything else is.** Every ruling is a `GovernanceRuling` in the register (statement, enforcing shapes, source): query it, do not look for it here. Rule sets and profiles are in the register too. How each ruling came about is in `LINEAGE_RULING_NARRATIVES_v163_2_0.md`: history, read only when working on that ruling.

**Order of precedence.** The OE ceremony and OE Operating Discipline run first; a lineage grounded on unverified bytes is a lineage about nothing.

## Ceremony — before the first work item

1. **Declare the profile and level** as an owner decision with rationale, target and review date. Work done by agents opens under the agentic adaptive profile (AAL); otherwise under the non-agentic one (NAAL); AAL is the default profile and opens a lineage that names none. A clean result at a low level is a narrower claim, not a better one.
2. **Build the chain as a pipeline, one commit per stage:** Mission → ScopeStatement (text, exclusions, deliverables) → Goal → Objective → Backlog. Each stage closes in its own commit and records a `StageOutput`; the next stage consumes it. Git is the only witness of order, and it orders between commits, not within one. With a work branch (G203), each stage and box is pushed there when it closes and the order is read there.
3. **Date the objectives from a forecast, and read every date as a forecast (G186, G197).** Run `backlog_date_plan predict` on the lineage: it shows the expected completion from the work still to do and the pace delivered in earlier boxes; discuss it with the Owner before the dates are final and record that on the forecast (G198); keep the base dates; every box opened gets a base plan of its own (`backlog_box_step open` records its predicted end, G187), and run `backlog_date_report` for the base, updated and finished date of each objective and each box against its base plan (G188). **A date is a forecast of when the work is expected to be done at the pace delivered. It is never a target, a deadline or a promise, and it enforces nothing:** no scheduler exists, nothing waits for a date, work starts and ends when the work allows, and a date that passes makes nothing invalid (a passed date with no observation is an advisory about the forecast). Dates are read afterwards against what happened.
3a. **Name the kind of every obstacle (G189).** An impediment names one of seven kinds (rule refusing, evidence missing, tool at fault, wrong order, access limited, decision waited on, outside service failing); a lineage that adopts `RS_ImpedimentsKnown` is refused an impediment with none.
3b. **Clear an obstacle by a known way that keeps the rules (G190).** Each kind lists the ways known to clear it (`backlog_impediment advise`); a cleared impediment names the way used, and one that fits its kind. The ways are written to satisfy or change an obligation, not to waive, skip or defer it; that is a review point, not a check.
3c. **Raise an obstacle the moment it stops work (G191).** `backlog_impediment raise` names the box whose work it blocks (G199), its kind and its owner; `clear` names the way used. `backlog_agent_monitor` lists every open obstacle in hours; `backlog_date_report` names those that stood in a late box.
3d. **Derive the chain from the scope taxonomy, never from a list of gaps (G194).** The scope statement holds areas (places the work reaches), deliverables (what must become true) and exclusions (what is out). Items nest under one parent of their kind (G200). Every area is answered by a goal that faces the scope, a kept area by a containment goal, every exclusion by a goal that guards it, the mission by a mission-facing goal; each goal is measured by objectives and each metric is derived from its goal. A gap found later becomes a scope item by a change request, then a goal, then an objective, and only then a story.
3e. **Work reaches the register before it reaches a file (G194).** A change to an ontology, shape or tool file is the work of a story planned in a live lineage. The release gate passes it only when an item moved, or when the changelog's unplanned-work line cites a dated Owner ruling or an urgent interruption that the same release records; "None" fails. A release that only closes a stage of a lineage's chain is planned work and passes as such (G196). Enforced today by `backlog_release_item_check` and `OwnerRulingDatedShape`; the answering of every scope item by a goal and the parent-child link of the scope taxonomy are enforced by the work of the revived Lineage 29, and are rules of work before they are checks.
3f. **Mature in small steps.** Start from the smallest slice of the scope, plan it, do it, review it, read its objective, then enhance; a stage may be revised by a stage revision instead of restarting the lineage. This is the Owner's direction.
3g. **Route every instruction before the first file changes (G195).** An instruction that creates work is routed, and the route is recorded, before anything is written: (a) it serves the live lineage's mission: a change request, then a scope item, a goal, an objective and a story; (b) it has another purpose and cannot wait: the urgency is declared first (`backlog_urgency declare`), the urgent work lives in a lineage of its own and is built after the declaration; (c) another purpose that can wait: a queued lineage; (d) a change to the discipline or its rulings: the Owner's dated ruling, recorded in the same release. Work built before its route is set aside and entered through the route, never backfilled. The release gate refuses unplanned work whose cited authority is dated after the work, and a shape refuses an urgent item that started before its declaration.
4. **State the granularity** you chose and why (`LineageDepthAdvisoryShape` shows the symptom as an advisory).
5. **Decide how work reaches users:** planning event, iteration, deployment unit.

If a step cannot be completed from rules and facts, stop and state plainly what input is needed. Never backfill a bypassed chain; restart it.

## Principles (ontology-native)

- **A rule is a shape.** A lesson becomes a shape and a `GovernanceRuling` that names it. Rulings are never kept as prose. What no shape can reach is recorded as a ruling that says so.
- **Connections are links, never text.** A reference to a modelled thing is an object link.
- **Order is witnessed, not declared.** A digest computed from the finished state proves nothing about order. Checked by `backlog_lineage_order_check` in the release gate.
- **A ruling binds only work not yet started.** Lineages adopt rule sets when they open; the register adopts rule sets by owner decision (`ObligationAdoptionShape`).
- **Append, never edit.** Corrections are added with a note; history is not fabricated; a superseded item stays visible.
- **Completion is not accomplishment.** Objectives are measured; a scope has deliverables of its own (`L4MeasuredObjectiveShape`, `ClosureReportShape`); a figure that cannot fall measures nothing.
- **A tool that refuses is not thereby correct.** Check tools with fixtures whose answer is known; run at the level you enforce.
- **Publish each increment** after its gate passes; a lineage with a work branch commits each increment there once the checks of its kind pass, and releases the batch when its measures meet their conditions (G203). The gate has a cost budget; a chain-stage release that only adds records passes the light gate, and the fifth release of a batch runs the full one (G178). Checks that read no register are skipped while nothing they read has changed.
- **Simplify how a lineage is run, never the obligations it owes.**
- **Keep this file short.** It is checked against the shapes and held to a size ceiling by `backlog_lineage_discipline_check`.
